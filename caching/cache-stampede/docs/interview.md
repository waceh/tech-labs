# 시니어 백엔드 면접 질문

아래 답변은 설계 답변 예시입니다. 본인이 실제 구현하거나 측정한 경험으로 주장하려면 별도 근거가 필요합니다.

## Redis가 복구되었지만 캐시가 비어 있다면?

**의도:** 연결 복구와 서비스 회복을 구분하고 원본 용량을 보호하는지 확인합니다.

**답변 예시:** “먼저 복구 방식과 데이터 유실 범위를 확인하겠습니다. L1을 활용하고 동일 Key는 인스턴스별 Single Flight로 합치되, 다양한 Key의 miss에는 원본 동시성 제한과 빠른 거절을 적용하겠습니다. Hot Key Warm-up은 foreground와 합산한 DB 예산 안에서 낮은 우선순위로 진행하겠습니다. Redis hit ratio와 DB 지연·풀 대기·API 오류율을 함께 보며 트래픽을 점진적으로 늘리겠습니다.”

**꼬리 질문:** Warm-up이 DB 부하를 더 키우면? 인스턴스가 2배 늘면? stale이 허용되지 않는 데이터는?

**보완할 부분:** 정확한 permit 수나 회복 임계치는 데이터 없이 말할 수 없습니다. 장애 전후 트래픽, 원본 최대 처리량, SLO, 실제 Redis 영속성 구성을 제시하면 설계 판단의 근거가 됩니다.

## Single Flight는 100ms 동안 요청을 모으는 것인가?

**의도:** batching과 in-flight 공유를 구분하는지 확인합니다.

**답변 예시:** “시간 창으로 모으지 않습니다. 첫 요청이 즉시 작업을 시작하고, 작업이 끝나기 전에 도착한 동일 Key 요청은 같은 Future의 결과를 기다립니다. 완료 이후의 재사용은 캐시 책임입니다. Batching은 서로 다른 Key를 시간/크기 기준으로 모아 일괄 호출할 수 있습니다.”

**꼬리 질문:** 원본이 10초 멈추면? 요청 하나가 Future를 cancel하면? 결과가 mutable이면?

**보완할 부분:** 요청별 Future copy와 대기 timeout만으로 원본을 중단시키지 못합니다. 원본 deadline, Key/follower 수 제한과 cancellation 정책까지 설명해야 합니다.

## 10개 인스턴스에서 DB 조회가 정확히 한 번인가?

**의도:** 로컬 동시성 제어와 분산 coordination의 범위를 이해하는지 확인합니다.

**답변 예시:** “로컬 Single Flight는 같은 객체에서 같은 Key의 실행 중인 작업만 합칩니다. 10개 인스턴스가 동시에 miss라면 각 인스턴스에서 1회씩 실행될 수 있습니다. Redis 공유 캐시가 이후 조회를 줄일 수 있지만 원자적인 전역 leader 선출은 아닙니다. 전역 중복 억제가 필요한지, 중복 읽기를 용량 안에서 허용할 수 있는지 먼저 판단하겠습니다.”

**꼬리 질문:** Redis 분산 락을 쓰면? 락 lease가 만료되면? Redis 장애 중에는?

**보완할 부분:** 락 획득뿐 아니라 미획득 요청의 행동과 늦은 결과 게시도 설명해야 합니다. 분산 락은 exactly-once나 정합성의 일반 해답이 아닙니다.

## 캐시 무효화 이후 오래된 값이 다시 들어오면?

**의도:** cache-aside의 stale write 경쟁을 이해하는지 확인합니다.

**답변 예시:** “DB 갱신 전에 시작된 조회가 늦게 완료되어 예전 값을 게시할 수 있습니다. Single Flight는 읽기 중복을 줄이지만 쓰기와의 정합성을 보장하지 않습니다. 허용 지연을 먼저 정하고 version/세대 기반 조건부 게시와 이벤트 무효화, TTL 보정을 검토하겠습니다.”

**꼬리 질문:** 이벤트가 순서 역전되면? version 정보도 삭제되면? L2만 지우면 L1은?

**경력 연결:** RabbitMQ 기반 OES와 Kafka 파이프라인 경험을 연결할 수 있습니다. 실제로 다룬 중복, 순서, 재처리 정책을 구체적으로 설명하되 해당 시스템에 없던 기능을 구현했다고 말하지 않습니다.

## 실험 결과를 어떻게 설명할 것인가?

“100개의 원본 조회가 겹치도록 Latch로 제어한 실험에서 cache-aside는 100회, Single Flight는 1회였고 이후에는 L1을 재사용했습니다. 서로 다른 Key와 별도 인스턴스는 합쳐지지 않는 것도 확인했습니다. 실제 DB/Redis와 RPS·P99를 측정한 결과는 아니므로 운영 성능 개선 비율로 해석하지 않습니다.”

시니어 면접에서는 패턴의 이름보다 **원본 용량, 장애 전파, 정합성, 검증 범위와 Trade-off**를 함께 설명하는 것이 핵심입니다.
